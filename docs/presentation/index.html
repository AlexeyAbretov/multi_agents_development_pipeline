Содержание

О чём эта презентация

Процесс

  • Зачем оркестратор и чем он не является
  • Роли: аналитик, разработчик, тестировщик, релиз-менеджер
  • Автомат labels на GitHub Issue
  • QA-цикл, MVP и календарный релиз

Как устроено

  • Поллинг GitHub, без входящего webhook
  • Cursor Cloud только для процесса
  • MongoDB-журнал джоб и локальный UI очереди
  • Гейты человека: merge, milestone, апрув плана

Ветки пайплайна — pipeline/N-…. Merge в main только после явного подтверждения.

02 / 16
Проблема

Цикл разработки не должен жить в чате

Без оркестратора

  • План, код, QA и релиз размазаны по ручным шагам
  • Агент может «заодно» расширить scope или замержить в main
  • Нет идемпотентности: легко запустить второго агента на ту же задачу
  • Релиз по догадке, а не по дате milestone

С пайплайном

  • Источник правды — labels на GitHub Issue
  • Роль выбирается правилами, не настроением модели
  • Одно активное облачное задание на пару (issue, role)
  • Человек решает, что попадает в main и когда выходит версия
03 / 16
Граница репозитория

Это оркестратор, не продукт

Этот репозиторий

  • Оркестратор, UI очереди, промпты ролей
  • Конституция, контракт, статусная модель
  • Целевой продукт задаётся конфигом: GITHUB_REPO, CURSOR_REPO_URL
  • Код каталога сюда не импортируется

Целевой продукт

  • Отдельный GitHub-репозиторий
  • Свои issues, PR, milestone, Releases
  • Облачный агент читает файлы продукта
  • Runtime продукта остаётся на машине разработчика

Один git remote — GitHub. Локальная Gitea пайплайном не используется.

Роли

Четыре облачных агента и человек

Роль Делает Не делает
Аналитик План в issue; для MVP — задачи после апрува Код, merge
Разработчик Ветка issue/<n>-…, pull request Merge в main
Тестировщик Issue-QA по PR или регресс main Tag, Publish, E2E без локального прогона
Релиз-менеджер Changelog и published GitHub Release по milestone Draft, merge, релиз без зелёного регресса
07 / 16
Автомат feature / bug

Labels — источник правды процесса

bug / feature + needs-plan → in-analysis → ready-for-dev → in-dev → in-qa → qa-in-progress → qa-passed → человек мержит PR

Параллельный тик

Analyst, developer, tester и RM стартуют в одном полле параллельно. Роли не ждут друг друга. Повтор той же пары (issue, role) блокирует MongoDB-замок.

Стоп-кран

needs-human режет все роли. После ошибки Cursor человек снимает метку и возвращает trigger-label — замок сбрасывается, агент стартует снова.

После qa-passed на feature/bug автоматика останавливается. Релиз-менеджер от этой issue не вызывается.

08 / 16
QA-цикл

Дети-баги, глубина 1, не больше трёх кругов

Как устроен цикл

  • Tester пишет PIPELINE_BUG_ISSUES
  • Максимум 2 блокера за прогон; nit — комментарий в PR
  • Дети: bug + needs-plan, Related to родителя
  • Родитель остаётся in-qa, пока дети открыты
  • Потом сброс джоба tester и re-QA

Ограничения

Глубина дерева = 1. fix-round ≤ 3. Четвёртый круг разработчика → needs-human.

09 / 16
Старт проекта

MVP: план → апрув человека → очередь задач

mvp + needs-plan → in-analysis → to-approve → человек: approved → создание feature/bug → MVP закрыт

Порядок разработки

Маркер PIPELINE_MVP_TASKS: 12+14,16

  • + — один этап, задачи параллельно
  • запятая — следующий этап
  • developer идёт по этапам; analyst и tester — параллельно

Гейт человека

  • План не нравится — снова needs-plan
  • План ок — снять to-approve, поставить approved
  • На MVP не стартуют developer, tester и RM
10 / 16
Календарь

Человек задаёт дату, RM публикует Release

Milestone = будущий релиз

  • Title строго vN.N.N
  • due_on — день Publish, календарь Europe/Moscow
  • T−1: служебная issue «Регресс vN.N.N»
  • T: RM, если регресс зелёный и нет открытых work-items

Стоп до Publish

Нет коммитов с прошлого tag → milestone закрывается, Release не создаётся. Красный регресс, needs-human или открытые bug/feature/mvp → blocked: no release.

11 / 16
Статусы

Три слоя, три разные правды

1. GitHub labels

Процесс продукта. Оркестратор читает labels, запускает роль и переписывает их. Без нужного label тик issue не увидит.

needs-plan in-dev qa-passed

2. Job в MongoDB

Идемпотентность оркестратора: одно активное облачное задание на (issue, role). История не стирается, замок можно сбросить.

queued running finished

3. UI-статус

Проекция для человека. finished + needs-human → «уточнение». Ошибка Cursor → «ошибка».

выполняется уточнение ошибка

После рестарта джобы running/queued помечаются error + cleared: облачный агент уже мёртв, запись журнала остаётся.

12 / 16
Стек и протокол

Правила чистые, поллер ходит наружу

Код

  • Node ≥ 22, TypeScript, Fastify, Zod
  • @cursor/sdk — только cloud runtime
  • GitHub — ручной REST, без Octokit
  • MongoDB: jobs и schedule-state
  • UI: React, Vite, Tailwind, опрос раз в 5 с

Маркеры в ответе агента

  • PIPELINE_LABELS: — исход роли
  • PIPELINE_BUG_ISSUES: — блокеры QA
  • PIPELINE_MVP_TASKS: — порядок этапов
  • PIPELINE_RELEASE_TAG + changelog

Оркестратор сам меняет labels и создаёт Release. Агенту нельзя доверять GitHub напрямую.

14 / 16
Контур человека

Автоматика ведёт процесс, человек держит контроль

Всегда человек

  • Merge PR в main после issue-qa-passed
  • Дата релиза: open milestone vN.N.N с due_on
  • Апрув плана MVP (to-approve → approved)
  • Возврат из needs-human

Агентам запрещено

  • Merge в main
  • Релиз без зелёного регресса
  • Утверждать E2E продукта без локального прогона
  • Расширять scope «заодно» и коммитить секреты

При сомнении — needs-human, не «лучшая догадка».
