# Конституция

> Неизменяемые правила репозитория оркестратора.  
> Контракт (labels, роли, триггеры): [AGENT_PIPELINE.md](./AGENT_PIPELINE.md).  
> Запуск: [AGENT_PIPELINE_SETUP.md](./AGENT_PIPELINE_SETUP.md).

Владелец документа — человек. Агенты не переписывают конституцию и контракт пайплайна без `needs-human` и явного апрува.

Целевой продукт (каталог, API, runtime) живёт в **другом** репозитории и может иметь свою конституцию. Облачные агенты читают файлы **продукта**. Этот файл — закон **этого** репо.

---

## 1. Назначение

Этот репозиторий — **только** оркестратор, deployer, UI очереди и промпты ролей.

Он поллит GitHub Issues целевого продукта, запускает Cursor Cloud (аналитик → разработчик → тестировщик → релиз-менеджер) и по published Release деплоит продукт **на машине разработчика**.

Не импортировать код продукта. Не хардкодить URL конкретного продукта: только плейсхолдеры в `.env.example`. Связь с продуктом — конфигурация:

| Переменная | Где | Зачем |
|------------|-----|--------|
| `GITHUB_REPO` | `pipeline/.env` | Issues / PR / Releases продукта |
| `CURSOR_REPO_URL` | `pipeline/.env` | Что клонирует Cursor Cloud |
| `PRODUCT_WORKSPACE_HOST` | корневой `.env` | Checkout продукта для `deployer` |

## 2. Принципы

### P1. Процесс в облаке, продукт на машине

Для **процесса** разработки разрешены GitHub и Cursor Cloud (клонирование репо на VM, API).

Для **продукта** (данные, фото, MongoDB, Ollama, runtime каталога, `docker compose` продукта) — только локальная машина разработчика. Облачный агент не деплоит и не запускает compose продукта.

Исключение из «всё только локально»: исходящий HTTPS с ПК на `api.github.com` и API Cursor. Входящий туннель и webhook на оркестратор — вне конституции, пока человек явно не изменит этот пункт.

### P2. Один git remote — GitHub

`origin` — GitHub. Локальная Gitea пайплайном не используется.

### P3. Поллинг, не туннель

Оркестратор только **исходящие** запросы. Нет входящего webhook, нет Cloudflare Tunnel в первой волне.

### P4. Человек задаёт дату релиза; RM публикует при зелёном регрессе

Человеческий gate на релиз продукта — **open milestone** с title `vN.N.N` и `due_on` (дата создания GitHub Release).

Облачный релиз-менеджер **может** создать published GitHub Release (tag = title milestone), если регресс `main` прошёл. Draft Release не используются.

Агенты **не** мержат в `main`, **не** деплоят. Деплой — только локальный deployer по уже published Release.

Сдвиг `due_on` или новый hotfix-milestone — тоже действие человека.

### P5. Секреты не в git

Не коммитить `.env`, `pipeline/.env`, токены, ключи. В репозитории только `.env.example` с плейсхолдерами.

### P6. docker.sock только у deployer

Контейнер `orchestrator` сокет не монтирует. `pipeline-ui` — таблица очереди, без кнопки апрува релиза и без docker.sock. UI слушает `127.0.0.1:3010`, в интернет без защиты не публиковать.

### P7. Идемпотентность

Одно активное облачное задание на пару `(issue, role)`. Один деплой на tag. Состояние — volume (`jobs.json`, `deploys.json`, …), не «память» контейнера.

### P8. Минимальный scope

Не расширять задачу «заодно». Вне scope первой волны (автоmerge, webhook, Telegram, деплой на VPS, E2E vision на каждый PR) — только по явному запросу человека. Задача вне MVP продукта → `needs-human`, не реализация.

### P9. Нет merge в `main` без апрува человека

Для продукта: агенты не мержат. Merge PR в `main` делает **человек** после `qa-passed` этой issue (или явное «ок» в чате разработки пайплайна). Это не апрув релиза: к регрессу `main` код уже должен быть в `main`.

Для **этого** репозитория оркестратора: merge в `main` только после явного подтверждения пользователя («мержим» / «этап готов» / «ok»). Автоmerge вне scope.

## 3. Git-workflow

### Репозиторий оркестратора (этот)

1. Перед этапом: `git checkout main` → `git pull` → `git checkout -b pipeline/N-…`
2. Коммиты только в ветке этапа. Один этап плана = одна ветка `pipeline/N-…`
3. Merge в `main` — только по команде человека (P9)
4. Следующий этап — новая ветка от обновлённого `main`
5. Не смешивать с ветками `stage/*` продукта

### Репозиторий продукта (целевой)

| Трек | Ветки |
|------|--------|
| Этапы MVP продукта | `stage/N-…` |
| Задачи пайплайна после плана | `issue/<n>-…` |
| Дочерний баг (`Related to #N`) | ветка от head PR родителя, PR **не** в `main` |

Разработчик открывает PR, не мержит. Тестировщик не утверждает E2E vision / поиск / Ollama без локального прогона.

## 4. Стек этого репозитория

| Часть | Технологии |
|-------|------------|
| Оркестратор / deployer | Node ≥ 22, TypeScript, Fastify, Zod, `@cursor/sdk` (явно `cloud`) |
| UI | React, Vite, TypeScript, Tailwind; порт `127.0.0.1:3010` |
| Прогон | Docker Compose из корня; `orchestrator` `:3020`, `deployer` `:3021` |
| Язык | Промпты, комментарии GitHub, коммиты — **русский**. Код — TypeScript |

Порты оркестратора и UI не смешивать с портами продукта. Ollama не входит в compose пайплайна.

## 5. Документы

Источник правды после merge — файлы в git, не тело PR.

| Документ | Роль |
|----------|------|
| Этот файл | Принципы; меняет только человек |
| [AGENT_PIPELINE.md](./AGENT_PIPELINE.md) | Контракт процесса; агенты не переписывают без `needs-human` |
| [AGENT_PIPELINE_PLAN.md](./AGENT_PIPELINE_PLAN.md) | Чеклист этапов `pipeline/N-…` |

Аналитик в плане перечисляет, какие docs править в том же PR. Расхождение docs и diff — дефект, если ломает критерий issue.

## 6. Запрещено

- Merge в `main` без P9
- Деплой и `docker compose` продукта с облачной VM
- Коммитить секреты
- Hardcode URL конкретного продукта в коде
- Импорт кода продукта в оркестратор
- Утверждать E2E продукта без локального прогона
- Кнопка Publish / апрува релиза в UI пайплайна (релиз — GitHub Release, который создаёт RM по milestone)
- Копировать полный транскрипт Cursor в UI; достаточно ссылки на `agentId`

При сомнении — `needs-human`, не «лучшая догадка».

---

## 7. Изменение конституции

1. Человек формулирует правку (issue или явное поручение).
2. Ветка `pipeline/N-…` (или отдельный PR), не «заодно» с фичей.
3. Merge в `main` — только после явного «ok».
4. После смены принципа проверить контракт, промпты `pipeline/prompts/` и `.cursor/rules/`.
